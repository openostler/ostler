# ADR-0001 — Adopt Vibes as Code

- **Date:** 2026-09-30
- **Status:** accepted

## Context

Governance was spread across a 139-line root CLAUDE.md and SCOPE.md. There were 40+
markdown files with no metadata, `docs/` and `references/` overlapped, and three docs
gave three different test counts. Agents had to open bodies to discover what existed.
The maintainer's other projects use Vibes as Code.

## Decision

Adopt Vibes as Code for the documentation layer:
- `CONSTITUTION.md` holds the hard rules.
- `INDEX.md` is generated by `skill/scripts/build_index.py`.
- Every manifest-eligible `.md` has frontmatter, checked by
  `skill/scripts/validate_frontmatter.py`.
- Every directory has a small `CLAUDE.md`.
- Decisions live in `decisions/`, and designs in `specs/`.

The scripts are vendored from the upstream Vibes-as-Code repo, with a project-specific
area enum and exclusions.

## Consequences

- Easier: an agent loads INDEX and CONSTITUTION (~5k tokens) and then only the
  documents it needs.
- Easier: CI rejects undocumented docs.
- Harder: every new doc needs frontmatter, and every doc edit needs an index rebuild.
- Existing docs over 300 lines are flagged by the validator as warnings. They are split
  in a follow-up, not in the adoption commit.

## Alternatives considered

- Keep the ad-hoc CLAUDE.md. Rejected: it does not scale past ~40 docs, and the drift
  is already visible.
- Import the Vibes scripts as a git submodule. Rejected: the area enum is project-specific,
  and a submodule complicates tester installs.
